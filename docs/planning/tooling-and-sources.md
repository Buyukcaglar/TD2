## DOS reconstruction workflow recommendation

The following are engineering proposals/inferences from the source capabilities and the project's preservation goals. They are not verified descriptions of Test Drive II internals.

1. **Preserve identity before interpretation.** Record complete-file hashes, size, relative path, header facts and edition provenance. Originals stay in `reference`; use an isolated derived directory for every future transform. Record command, tool version/hash, input/output hash and whether an operation modifies headers, relocations or padding.
2. **Resolve packing before game-function recovery.** The parent/local DOS inspection reports an `RB` marker at stub offset `0x10`, entry offset `0x12`, and the English EXEPACK error marker. These agree with SRC-EX-01 and strongly support the EXEPACK family. Exact stub/version and unpacked image remain unverified. Future work must compare stub bytes, validate every EXEPACK length/boundary, then produce a derived unpacked image only after development authority. A guessed string boundary is insufficient. No unpacker was executed in this phase.
3. **Validate a transformed image independently.** Check entry, stack, image bounds, expected packed/unpacked lengths, relocation count/ranges and trailing-data disposition. Compare a second implementation or a later controlled post-unpack memory image. Record equivalent relocated words separately from raw image bytes. A successful decompressor exit is one tool result, not recovery acceptance.
4. **Import with explicit address provenance.** Select the real-mode x86 language/MZ loader as appropriate to the confirmed image. Save language/compiler specification, analysis base, relocation status, memory map, import diagnostics and tool build. Keep three addresses when applicable: original file offset, module-relative segment:offset, and analysis/run load address. For unpacked code without a direct original-byte mapping, point to the transformation record rather than inventing one.
5. **Treat decompilation as hypotheses.** Manually recover DS/ES/SS lifetimes, near/far pointer intent, aliased addresses, calling conventions, register arguments, callee/caller stack cleanup, indirect targets, signedness and 16-bit arithmetic. Annotate code/data boundaries and unreachable regions with confidence. Separate compiler runtime recognition from game semantics. Recheck each portable function against instruction-level effects and admitted test vectors.
6. **Model hardware interfaces explicitly.** List BIOS/DOS calls, installed interrupts, direct memory accesses and port accesses. Later isolate each behind typed interfaces. Preserve observable arithmetic overflow and timing/event order deliberately; do not embed host pointer layout or wall-clock dependence into the portable core.
7. **Compare CGA only after an EGA map exists.** Establish common functions and variant-only behavior through structural, data-flow and later runtime comparison. Graphic differences do not imply the remaining code is identical. Keep an independent coverage/evidence row for every original function, including stubs, drivers and unreachable candidates.

Recommended future oracle setup: a pinned debugger-capable DOSBox-X build, pinned config and working copy of one admitted game edition. Record CPU core/model/cycles, graphics machine, memory configuration, sound devices, RTC/time, DOS environment, save state and inputs. Before using replays as a differential oracle, repeat the same fixture and compare selected semantic states, framebuffer outputs and audio events. Establish repeatability empirically. Save states are useful checkpoints, not cross-version interchange or a determinism guarantee. DOSBox-X instruction timing is an approximation (SRC-DX-02); if a discrepancy depends on real hardware cycles, use a separately justified hardware or higher-timing-fidelity validation route.

## Resources, sound, and Windows-host recommendation

Start with a byte/accounting and consumer graph rather than one decoder per extension. The parent reports differing PCS first-byte groups and all surveyed PES first bytes equal `0x82`; these are clustering observations, not an identified compression algorithm. Prove each record layout from executable consumers and bounded samples. Document endianness, units, ranges, cross-file references, decompression limits, palette/mask rules, unknown fields, and unused/trailing bytes. Keep decoded previews and proprietary derived dumps local; release loaders and format descriptions without bundling original game data.

Use a portable C core with fixed-width, explicitly specified arithmetic and a small host interface. C17 is a reasonable proposed baseline, subject to the later build/portability decision. Prefer a software reference renderer and deterministic event timeline first. SDL3 is a conditional host-layer recommendation for Windows input, a streaming output texture and PCM delivery. Keep SDL types and callbacks outside core public state. Pin SDL/toolchain versions when implementation begins; no dependency was installed for this plan.

The user-confirmed DOS sound target is **PC Speaker music and sound effects**. Recover their reachable initialization paths, resource consumers, timer sequencing, effect priorities and hardware access, followed by controlled captures when runtime work is authorized. `VOICES.BIN` is reported locally as only CR LF; that cannot establish a sound bank. The user's scope correction does not substitute for implementation recovery or runtime validation. Select a portable event-timed speaker synthesis path only after the original pitch/divisor and timing rules are documented.

## Amiga recovery and source-comparison recommendation

The supplied Amiga archive is reported by local inspection as a flat installed distribution with a JF Fabre HD installer/patch README, `DuelHD`, and Hunk executables; **it has not been established as a WHDLoad package**. Do not replace that provenance with the external WHDLoad material. Archive listing identity, installer assignments, original executable bytes, launcher patches and any later slave are separate layers.

Future Amiga work should identify executable hunks/relocations, library calls, overlay load/unload transitions, graphics/DMA/audio register use, and original-versus-launcher modifications before decompilation. Import validated 68000 code at documented Hunk-relative locations; capture relocation/load maps, and revisit code reached only after overlay transitions. Hunk files named `song`/`sfx` must be inspected as possible executable replay components; do not feed them directly to a generic module player on their names alone. Use the proven ILBM and 8SVX standards only for files whose chunks validate. `Rpck`/`PPkc` markers reported locally are leads until a consumer or validated implementation proves the wrapper/compression variant.

The WHDLoad installer/source pages are useful **comparative patch evidence**. The newer .net page discusses a 108868-byte `duel` variant, but size agreement alone does not prove byte identity. Its optional enhancement and fixes can change an oracle's behavior. Keep original, supplied HD-patch and modern-patch behavior distinct. Its patch offsets and named dynamics/render helpers could accelerate original recovery after byte matching, but are modifications rather than original publisher source. Before reuse, resolve source licensing and map each patch to admitted original bytes. The package was downloaded for source-only text inspection; see [the examination record](evidence/whdload-source-examination.json) for exact hashes and limits. No binary was executed and no source was built.

The .net page gives package creation and slave/listing timestamps on 2026-10-11; its change history dates features/fixes to October 7/8. These are separate update/build dates, not proof of a contradiction. The .de page served the older 2021 distribution during this check. `TestDrive2HD.s` declares Public Domain in its header, while no explicit license/copyright text was found in the five other inspected source members. That absence does not establish their licensing.

For optional user-supplied Amiga scenery, inspect local pack indices and identifiers before relying on the external installer's merge helper. The complete small `datmerger.c` was read: it combines two byte-counted lists into one output with a terminator. Its assumptions and byte handling need independent validation before any reuse. Define duplicate/conflicting-ID behavior and distinguish car packs from route/scenery packs. Exact supplied content and executable consumers decide admissibility; the external tool's names/support claims are leads.

For native Amiga audio, recover sequencer state, sample ownership, pitch/period updates, looping, volume, channel assignment, filter/panning policy, and PAL/NTSC timebase from actual routines. Generic sample decoding alone is insufficient for music reconstruction. Reconstruct its event stream and compare to separately recorded original outputs. These are investigation cases, not a claim that Test Drive II uses a particular tracker, channel allocation or filter.

## Switching and validation implications

Live switching should change presentation/audio adapters over one canonical simulation. First prove semantic mappings between editions: car/scenery identity, coordinate conventions, animation phase, palette role, music cue/effect identity and duration. Additional Amiga scenery also requires proven normalized route geometry, collision/event rules and content indices, rather than a graphics-only swap. Leave unmapped items explicitly unsupported until evidence resolves them. Preflight target assets and prepare presentation state before committing a switch at a known boundary; preserve gameplay state, inputs, RNG state and simulation tick. Audio should have a specified handover policy with no stuck notes or stale sample references. Test switching repeatedly during menus, races, transitions, paused states, crash screens and music/effect overlap after each backend has independent fidelity evidence.

Separate gates: static byte/format evidence; reviewed pseudocode/contracts; portable-C compilation; deterministic unit/differential state checks; runtime gameplay exercise; visual/audio acceptance; original-edition fidelity. None substitutes for the next. Timing estimates should be revised after packing validation and a representative gameplay/resource vertical slice; tool availability and file counts alone cannot support a credible completion date.
