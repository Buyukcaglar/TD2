# Amiga version: files, findings and plan

Started 24 October 2026. The source is the user's archive `reference/amiga/TestDrive2&DataDisks_v1.1_HD_JOTD.lha`: Jean-François Fabre's HD install of the Amiga game with its car and scenery disks. `docs/planning/amiga-evidence-and-plan.md` is the earlier inventory (file hashes and first bytes); this file replaces its plan.

For the tools, unpack the archive once into `runs/amiga` (gitignored): the app does this itself when the archive is added under Game files, and `runs/amiga` is a copy of that folder. All tools below read from there.

## 1. What is in the archive

| Folder | Content |
|---|---|
| root | `duel` (the game), `DuelHD` (the HD patch loader), the catalogues `cars.dat0`, `scen.dat0`, `select.dat0` |
| `cars` | Ferrari F40 and Porsche 959 (base disk) |
| `cars1` | The Muscle Cars: `camo`, `dodge`, `gt500`, `gto`, `stingray` |
| `cars2` | The Supercars: `coun`, `lotu`, `ross`, `ruf`, `vett` |
| `pics` | title, option and difficulty screens, game over, end game, the road sprites |
| `scen` | Master Scenery (`sc1_`, 6 stages) |
| `scen1` | California Challenge (`rock_`, 7 stages) |
| `scen2` | European Challenge (`euro_`, 6 stages) |
| `scen3` | Northern Germany Challenge (`euro_` names again, 7 road files). Its title picture reads "2012 Janusz_Mombasajoe" and names Ostsee, Lüneburger Heide, Wesertal, Teutoburger Wald, Harz and A7. |
| `sfx` | samples and the music player `song` |

The catalogue files have the same records as the DOS `CARS.DAT` and `SCENES.DAT`: a count, then a path (`cars/p959`, `scen/sc1_`) and a display name per entry, big-endian.

**Northern Germany is built from the other sets.** It is a scenery made in 2012 for the Amiga game (its title picture credits Janusz "Mombasajoe"; its catalogue entry still says "Euro. Challenge"). Every sprite file in `scen3` is a byte copy of a Master, California or European file, under another name (for example its `euro_mercedes.shp` is the European `euro_thunderbird.shp`). All seven road files are copies of roads of the other sets; `euro_roaddata1`, the one that looked new, is the Master `sc1_roaddata2` with only the sprite file name changed (`treesmountai1.shp`). New are six of the seven sign files (Baltic coast towns, the Weser, the Teutoburg Forest, the Harz, German warnings), the title picture `euro_icon` and its high scores. See "Northern Germany in the port" below.

## 2. File formats found

- **Program files** (`tools/amiga/hunk.py`). `duel` is an AmigaDOS load file: 71 KB code, 31 KB data, and an overlay node of 21 KB code. The overlay node is a load file of its own inside `duel` (at file offset 15734h): one code hunk without relocations, which reaches the root's data A4-relative and its code through A4 stubs. The root calls into it through the overlay manager's stubs at `$21a00`–`$21a38` (a `bsr.w` to the manager, then the node and the offset). `hunk.load(..., overlays_too=True)` lays it out at 2A000h; `disasm.py` and the image `hunk.py` writes include it (the Ghidra decompile in `runs/amiga-ghidra` was made before and does not). The overlay holds the title sequence, the car showroom, and the 8SVX effect calls. It is compiled C (Lattice/SAS style: small data through A4, `link`/`unlk` frames), with no symbols. `sfx/song` is a separate load file with its symbols: the music and effect player (`_PlaySong`, `_PlaySfx`, `_StopSong`, `_FadeSong`, `SongInt` and so on, 3 KB of code) and 21 KB of chip-memory data (the song and its instruments). `tools/amiga/disasm.py` disassembles with Capstone's 68000 mode at the addresses `hunk.load` gives.
- **Rpck packing** (`tools/amiga/rpck.py`). 177 files start with `Rpck`, the unpacked size and a run-length stream: a signed count byte, a run of `n + 1` copies for `n ≥ 0`, `-n` literal bytes otherwise. The loader is at `$1e5d0` in `duel`, the unpacker at `$1e518`. `tests/test_amiga_files.py` runs the game's own unpacker under Unicorn (as a 68000) on all 177 files and compares with the Python one: all match. Six streams write one byte past the stated size; the game's buffer takes it.
- **Pictures** (`tools/amiga/ilbm.py`). Full screens (title, options, difficulty, the dashboards, the rear views, the scenery title pictures, the gas stations) are IFF ILBM, 320 × 200, 5 bitplanes (32 colours), ByteRun1. The `.p` files are palettes alone: ILBMs of one pixel for the two base cars, and for the data disks' cars a bare `CMAP` chunk whose length field is garbage (duel's `$108a4` looks for `CMAP` and takes the 32 colours after its header; the port's readers do the same). The `.sb` files are 640 × 200 in 4 colours. All decode and look right.
- **Sprite archives** (`.shp`, Rpck-packed; `tools/amiga/shp.py`). They are the DOS archive layout, big-endian: a long (`PPkc` or a size), an entry count, the 4-character names, the offsets, the data. The names follow the DOS names, so a DOS sprite can be matched to its Amiga sprite by archive and name.
  - Each sprite is a 20-byte header and its bitplanes, one after the other: width in bytes, height, hot spot x and y, screen position x and y, a byte of planes the sprite clears and a byte of planes it sets wherever it is drawn (+12 and +13, as duel's blit `$1f0f6` uses them; +12 is always the planes the stored ones leave out), and up to six bytes that say which screen planes each stored plane goes to (a stored plane may go to several, `03` or `1f`). Colour 0 where no stored plane is set is transparent.
  - Checked: the dashboard's turbo gauge and fuel and oil gauges, drawn at their stated positions, equal the dashboard picture pixel for pixel (a test in `tests/test_amiga_files.py`). The roof, pillar, mirror, hood and steering wheel land where they belong.
  - **The race screen's palette** (answered). duel shows its screens through views of its own, built into a copper list it installs itself (`$15872` writes COP1LC): `$14820` adds a copper wait, `$1487e` a wait and colour moves from a table, and `$14dc4` builds the list from a linked list of viewports. A viewport has its palette at +98h, its position at +A0h, and optionally a second palette at +9Ch from line +92h, for which the copper reloads only the colours that differ (`$149a4`). The car loader (`$1bab0`) loads the dashboard picture, copies its 32 colours into the race viewport's second palette and sets the split at line 116 (+92h = 74h, on with +94h = 1). The palette above it is the section's road colours: `$1beae` copies 32 words from 0A6h of the section's `<scenery>roaddata<n>` (`$165ec` loads it, Rpck-packed, n the section from 0). Their colours 16 to 31 are the car's inside (reds and greys for the roof, pillar, mirror and hood); 0 to 15 are the scenery's.
  - Open: the gear gate (`gbox`) and the speedometer and rev counter masks (`spmC`, `tcmC`) come out scrambled with either palette, so their bitplanes are laid out another way. (Reading +12 as planes to clear, not to set, changes their colours but not that.) To be read from the cockpit drawing code.
  - Not all names match. The DOS archives keep separate EGA masks (`fc0M` next to `fcr0`). The Amiga road archive also holds the police car, which DOS keeps apart. The Amiga dashboard has more instruments (`fuel`, `oilp`, `oilt`, `trb0`, `swhl`).
- **Road data.** The DOS stage `.DAT` holds what the Amiga version splits over `roaddata<n>`, `slicedata` and `vectorsigns<n>`. `tools/dos_unpack.py` unpacks DOS files in Python (Huffman and RLE passes, archive entries) for these comparisons.
  - **DOS.** The road is a byte per road unit from DGROUP 3B51h (stage file offset 6E7h). Bit 7 is a side flag, and the low 7 bits index the stage's 128 records of 4 bytes at 347Eh (file offset 14h): flags, curve, pitch, object. The curves in those records run 0, 1, 2, 4, 6, …, -1, -2, -4, ….
  - **Amiga.** `roaddata<n>` is a header of 125 words, then the road bytes up to an `FF`. The loader is `$165ec`: it copies header words into game variables (many times 10) and takes the road length as the byte count less 2Dh. The header also names scenery sprite files (`desertmountain.shp`). `slicedata` is the same file in every scenery, and its values are the DOS record curves times 8, so it is the Amiga record table.
  - **Pairing.** The Master stages pair by number: each Amiga road is a little longer than its DOS twin (1426 against 1342 units for stage 0, and so on for all six). The road bytes are mostly the same runs with other record numbers (DOS `3b` where the Amiga has `46`) and some local differences.
  - **Records.** The Amiga record is two words: flags and curve (times 8) in the first, pitch and an object code in the second. Records 0–31 (straight, curves, hills, the flag records) are the same numbers in both versions. DOS records 32 and up carry the stage's own object numbers 1, 2, 3, …; the Amiga records carry global object codes, and Amiga record n is mostly DOS record n − 1 for n from 33 to 54. The Amiga uses about 40 further records (codes 16–20, 24–27, 39–41, 80–84, 88–91, 144–148, 152–155, 208–212, 216–219) that DOS does not have.
  - **Alignment.** With those rules the Master roads agree with DOS at 77 to 91 % (`difflib` over the road bytes). The rest is mostly the side flag: the Amiga sets bit 7 over long stretches where DOS has it clear, and the run lengths differ a little.
  - **How duel reads them** (answered 24 October 2026). The scene builder (`$17370`) reads the road bytes as DOS does (`project_rows`): the low 7 bits pick a record, its flags byte is XORed into a running state, its curve and pitch turn and tilt the road, and a change of bit 7 between neighbours marks where the road widens (DOS `DS_wide_toggle_ptr`). The width code (`$1746a`) adds the extra lane width while bit 7 is set, with an 8-unit ramp at each change, as DOS `widen` does. So bit 7 means the same in both games, and the long wide stretches and the 3 to 6 % longer roads are real differences of the Amiga edition, not a different reading. duel also interpolates the road width over up to ten ranges from the header (`+2Eh`, start, end, from, to; all zero in the Master roads), which DOS does not have.
  - **Objects.** DOS record byte 3 is a stage-local object code that drives a handler (`sim_motion.c`): 1–9 the road signs, 10 and 12 the white bands, 16h and up place a roadside sprite type `(code − 16h) × 5`, and 1Ch + q places billboard q of the stage's `.SGN`. The Amiga's codes are global; its billboard q is code 2Eh + q (2Eh–3Ah; 3Bh and up are other objects). Both games show the same billboards in the same order on paired roads. DOS scenery types pick five sizes of one sprite name group: 0 `sm0`, 5 `sm1`, 10 `md0`, 15 `md1`, 20 `lg0`, 25 `lg1`, then `hg0`–`hg9` (the names at the start of the EGA image's list). Every DOS scenery archive uses these names, so a stage can be drawn with another set's archive; a type the archive lacks is not drawn.
  - **Signs.** An Amiga vector sign file is the DOS `.SGN` in big-endian, except that the record's three palette colours become DOS's fixed white, green and black (three EGA and CGA pattern pairs), and DOS signs are about 4 % wider and 5 units taller. The California and European pairs show this for all 60 signs. The DOS font has no backquote.
  - Still to map: the header words and the DOS stage fields (the ratings are there: Amiga 70, 110, 150 mph against DOS 80, 110, 150).
  - **Northern Germany's roads** are, in order: California 6, a new road, Europe 3, California 2, Master 4, Europe 5, Europe 1.
- **Decompiling.** `tools/amiga/ghidra.ps1` lays out `duel` with `hunk.py`, imports it into Ghidra as 68000 code with A4 = `$2957e` (Lattice small data), marks a function at every `link a5`, and writes all 451 functions to `runs/amiga-ghidra/duel.c`. Global variables come out as their absolute addresses.
- **Sound.**
  - Five IFF 8SVX samples: `accolade`, `test_drive_ii`, `the_duel` (speech), `starter`, `gameover`.
  - Six raw samples with a small header: `Bump`, `crash`, `shortcrash`, `radar`, `siren`, `Squeal`. The race loads them in `$1cd1a` (short crash or crash by a setting); `$1ce50` plays the siren with its pitch swept between 14,000 and 23,000.
  - Each car's `engine` and `turbo` files (Rpck-packed in some cars).
  - `song`: the player and its data (below).

### The race sounds (in `duel`)

The race does not use the song player. `duel` has its own sample driver and the logic that feeds it from the car's state:

- **Driver.** Four channel records of 1Eh bytes at `$264a0` (A4 − 30DEh). `$11f96` sets it up: it takes the level 4 audio interrupt (`$1226e`) and adds a vertical blank server (`$1231c`). `$120cc` plays a sample on a channel (address, length, channel, period, volume, repeats; FFFFh loops), `$12072` plays a raw sample file at period 3,579,545 / its rate, `$1218a` stops a channel, `$121ea` tells whether a channel plays, `$12202` sets a channel's period and volume, `$12250` sets a channel's volume ramp (target and step, read by the server).
- **Raw samples.** `Bump`, `crash`, `shortcrash`, `radar`, `siren` and `Squeal` are a length (long), a rate in Hz (word) and signed 8-bit data. Their rates: bump 9,400, crash and short crash 5,326, radar 20,000, siren 7,202, squeal 10,000.
- **Logic.** `$1cd1a` loads the five race effects (crash or short crash by a setting). `$1d044` starts the looping sounds at the start of a race: the squeal and the car's engine and turbo samples. `$1d118` runs each frame: the engine's period is 2,398,600 / rpm (rpm at least 800, the period kept between 82h and 708h), and its volume comes from the gear and the speed. `$1d210` and `$1d2cc` play the gear change and the bump. `$1cde4` plays the radar beep, `$1ce10` the crash, `$1ce50` starts the siren and `$1cedc` sweeps its pitch between 14,000 and 23,000 (up by 1/50 or 1/100 a frame, down by 1/100).
- **The driver in C** (`src/amiga/race_sound.c`). Checked by `tests/test_amiga_race_sound.py`: duel's own routines run under Unicorn (A4 set, the OS call and the siren call replaced by `rts`). The C driver runs from `td2diff.dll`. Both play a script of raw samples, looping and repeating samples, period and volume changes, ramps, stops and the channel 6 alias, with the server every frame and the audio interrupts from the Paula timing model. Every custom chip write matches. A sample starts at the second frame after its channel last stopped, as on the Amiga. The original's marks for the game about channel 2 change no register and are left out.
- **The logic in detail.** Channel 0 has the one-shot effects and the siren, channel 1 the squeal, channel 2 the car's turbo sample (`<car>turbo`) and channel 3 its engine sample (`<car>engine`); each car has its own pair, raw like the effects. The logic reads these duel variables: the rpm (`$261fa`), the speed in mph as 16.16 (`$2619c`), the throttle (`$260f8`: below 0 braking), whether a working gear is engaged (`$262de` indexed by the gear `$26292`), whether the engine runs (`$26b38`), the skid squeal's volume (`$289d2`, set by the cornering code `$1b292` to 25 plus a sixteenth of how far the steering is past the grip limit, at most 64), the car's and the police car's road positions (`$25228`, `$26178`) and the police car's speed (`$26180`), two bump flags (`$262d8`, `$277ba`) and the gear change squeal's step (`$234ee`, set by `$1a71e`: a start from neutral into first above 4,000 rpm squeals for 25 − (rpm − 2,200) / 256 steps, a change into second with a drop of more than 1,600 rpm for 14).
  - The engine runs at full volume with the period above. The turbo runs at the engine's period; its volume is 0 when braking, and otherwise (rpm − 2,000) / 31.25 between 2,000 and 4,000 rpm in gear with the throttle on (nothing below 2,000 rpm or out of gear), plus (mph − 20) / 4 (at most 32), at most 64 in all, reached by a ramp of one step a frame. A car record word (offset 0Ah) of 0 would add 1,500 rpm and drop the turbo an octave; every shipped car has 1 there.
  - The siren's period is its pitch × 450 / (450 − the closing speed in mph) / its length (a 24-byte wave), changing by at most 2 % a frame; its volume is 64 less half the gap to the police car in road units (at most 60 less). The radar beep, the bump and the siren all use channel 0: the radar is not played during the siren or after a crash, the bump only when channel 0 is free.
  - duel calls Delay and WaitTOF between some plays; the C leaves them out, because the driver starts a sample no earlier than the second frame after its channel stopped anyway.
- **The logic in C** (`src/amiga/race_logic.c`). Checked by `tests/test_amiga_race_logic.py`: duel's routines from `$1cd1a` to `$1d30a` and its driver run under Unicorn, the C logic and driver from `td2diff.dll`. Both get the same car state (written into duel's variables for the original) over 450 frames of a scripted drive: revs through the gears, braking, coasting, a police car closing and falling back, radar beeps, bumps, gear change squeals, the siren started and stopped, a crash, a fade-out and a second start. Every custom chip write matches, and the test makes sure the siren swept, the gear change squeal played, the engine followed the rpm and channel 0 started its effects.

### The music and effect player (`sfx/song`)

- **What it is.** Accolade's player, 3 KB of 68000 code with its symbols, and 21 KB of chip data: one song (`titlesong`, four tracks), four instruments (bass, bass drum, snare, breathy flute, each an 8SVX in the file), the period and note length tables. Its entry point takes a command in D0: 0 open, 1 read the instruments, 2 play the title song, 3 stop, 4 close, 5 status, 6 fade, 7 play an effect (an 8SVX, channel, volume, repeats, music volume while it plays), 8 stop an effect, 9 effect status, 10 pause, 11 resume, 12 change an effect's rate and volume.
- **How it runs.** `SongInt` is a CIA-B timer A server; the song sets the timer itself (commands DD and DE, `3c00h` for the title song, about 46.6 ticks a second). Each tick reads note and command bytes per track, sets the voice, and starts notes with the period table, octave selection and vibrato or arpeggio. `SongIntHandler`, the audio interrupt, queues each sample's loop part or stops a one-shot. Effects take a channel from the music until they end.
- **In C** (`src/amiga/song.c`, from the disassembly, routine by routine). The song file is laid out by `amiga_mem.c` at the addresses `hunk.py` uses, and the player finds its variables by the file's symbols. Custom chip and CIA writes go through a hook.
- **Checked** (`tests/test_amiga_song.py`). The original runs under Unicorn and the C player runs from `td2diff.dll`. Both get the same timer ticks and audio interrupts, and a Paula timing model takes the interrupt times from the original's own register writes. Every custom chip and CIA write is the same, in order: 6,000 ticks of the title song (128.7 s, 1,986 notes, 1,546 interrupts), and a script with effects, rate changes, pause, resume and fade. The original has one oddity the C keeps: when it stops it clears the interrupt requests by writing to INTREQR, a read-only register, so that write does nothing.
- **Paula** (`src/amiga/paula.c`). Four DMA channels and the timer from the same register writes, stereo output as Paula wires it (channels 0 and 3 left, 1 and 2 right) with each byte held for its period, and a one-pole 4.4 kHz low-pass like the Amiga 500's fixed filter. It uses the NTSC clocks (3,579,545 Hz, CIA 715,909 Hz), because the player's effect periods are computed for NTSC. `python tools/amiga/play_song.py runs/amiga/sfx/song out.wav 130` renders the title song with it. Nobody has listened to it yet.

### The Amiga audio backend

`src/amiga/audio_amiga.c` is a second `AudioBackend` beside the PC speaker. The DOS game logic runs as before, speaker writes included; the Amiga backend ignores those and plays from the game's sound events and car state instead (`audio_backend.h`):

- **Events.** `music_play` reports its song, `run_stage` the start of each life (with the player's car code) and its end, with a crash or a blown engine before it, and `hit_object` the bump. Song 1 (title and menus) becomes the Amiga title song, reloaded from the file each time because the player edits its data. Songs 2 and 3 (the police ending) are silent: the Amiga game has no other song. A life's start stops the music, loads the car's engine and turbo samples (the DOS car codes map to the Amiga file names, `F40` to `cars/f40`, `GOAT` to `cars1/cars/gto` and so on) and starts the loops; its end fades them out and stops the siren.
- **Switching to it.** The DOS music player is game code and goes on in the game's memory whichever backend plays, so switching back to the PC speaker finds it where it should be. A switch to the Amiga sound starts duel's song at the same place: the host keeps the time since the game started its song and hands it to the backend (`song_at`), which runs duel's player that far without output (`paula_skip`, about 20 ms for 46 s). The DOS title song loops every 6049 ticks (60.49 s), duel's every 70.13 s (both measured): duel's arrangement is slower, so the place is the same fraction of the loop. Checked by recording both: after a switch at 40 s the music matches duel's song from 46.37 s.
- **Car state.** Ten times a second, at the start of the simulation's 10 Hz step, `sim.c` reports the rev counter's rpm, the speed, throttle, gear and whether it works, the skid (how far the steering is past the grip limit), the siren and radar flags, and both cars' positions and the police car's speed. The backend turns that into duel's variables, starts the gear change squeal as `$1a71e` would from two consecutive states, starts and stops the siren and the radar beep on their flags' changes, and runs duel's physics step `$1d118`. The vertical blank server (the siren sweep, then the driver) runs at the NTSC frame rate inside the Paula model.
- **Guesses.** duel runs its physics step about as often as the DOS game does (its free-revving adds 700 rpm a step where DOS adds 600 at 10 Hz), so the logic runs at 10 Hz. Road units and the steering scale are taken to be the same in both versions. Neither has been compared with a running Amiga.
- **Files.** The Amiga game's folder or archive is the `amiga` setting, chosen in the menu (Sound, "Amiga game files…") or when Amiga sound is first picked; `app_data_amiga_dir` finds the folder with `duel` and `sfx` in it, unpacking an archive into the profile first. The backend reads `sfx/song` and the five race effects at start and the car samples at each life's start.
- **8SVX sounds.** duel plays its one-shot 8SVX sounds through an overlay stub (`$21a10`; the overlay node's code at 5178h). That routine calls the music player's effect command 7 on channel 2, at volume 64, once, with the music at 69h meanwhile. The game over screen (`$13bc6`) plays `sfx/gameover` with it, and the title sequence (overlay code 13C6h–1640h, with `pics/title.shp`) plays `sfx/the_duel` and then `sfx/test_drive_ii`. The backend does the same at the DOS game over screen and at the DOS title picture ("tdri" and "duel"); the second speech sample starts when the first ends, where duel draws in between (a guess). `the_duel` and `test_drive_ii` are Rpck-packed; the backend unpacks them like duel's loader.
- **"Accolade presents".** `duel` starts the title song (`$10320`, overlay 51D6h) and then runs the intro (overlay 1204h). The intro loads `sfx/Accolade` and shows `pics/Title2`, the "Accolade presents" picture. It plays the speech with the same effect call and waits until it ends before the title sequence. (An earlier search missed the name because of its capital A.) It plays the speech only after the picture is in and the bar (`bull` of `pics/TitleCar.Shp`, `$2becc`) has slid in (`$2b2b8`), and not when a key ended the slide; the port sends the speech's event at that moment in both forms of the Accolade screen (it used to send it when the picture appeared, which the user heard as too early).
- **A sound before the song's first tick.** The music player's first tick of a song starts any pending effect and then turns all four channels off (DMACON 000Fh), which cuts that effect at once. On the Amiga the intro's disk loads come between the two, so this never happens. The DOS game shows its Accolade screen 0.09 s after starting its song, so the backend holds an effect asked for in that moment until the song's first tick; it looks every 5 ms. Without this the speech lasted 0.12 s of its 1.47 s.
- **The starter.** The showroom intro (overlay 1776h, called from the intro at `$2b776`, between "Accolade presents" and the title) plays `sfx/Starter`, an engine starting and revving. It loads the first car, shows it, loads the sound (`$2bb58`), waits 80 frames (`$2bb6a`), plays it with the same effect call if the sound is on, and waits 120 more frames before the car's window opens and the car drives off. The frames are vertical blanks: the wait counts the "Ticks VBLInt" server's counter. `$2beae` stops channel 2 when the intro ends or a key ends it. The backend gets `SOUND_SHOWROOM` when the DOS showroom's first car appears and `SOUND_SHOWROOM_END` when the showroom intro returns. It plays the starter 80 NTSC frames (1.33 s) after the first and stops it at the second. The DOS intro opens the window 150 of its ticks after the car appears.
- **The showroom's cars.** duel's intro shows the player's car, then the computer's: `$2b776` takes the car numbers and names the car choice keeps (`$251b0` and `$251b2`, then 16-byte names at `$251b4` and `$251c4`; the choice writes them at `$2de8c`) and loads `<name>.sideview.shp`. Before the first choice they are empty, the load fails, and it takes `cars/p959` and `cars/f40`. TD2's own intro always shows cars 0 and 1 (`0143:000a`). The port shows the chosen cars as duel does, with either sound and graphics (`showroom_intro_dos`); its choice starts with cars 0 and 1, so the first intro is TD2's. The shipped `SELECT.DAT` picks the RUF, so the snapshot runs and the Amiga graphics test write a `select.dat` of their own with the F40 and the 959. `tests/test_intro_cars.py` checks that the Camaro chosen stands in the showroom.
- **The intro's pace.** The pace follows the sound (the user's rule): with the Amiga sound the intro waits as long as duel's, so the pictures stay with their samples; with the PC speaker it keeps the DOS waits. Once there are Amiga graphics, the same rule gives Amiga graphics with the PC speaker the DOS pace. duel counts NTSC frames (it never checks for PAL), the DOS game 100 Hz ticks. From duel's intro (overlay 1204h at `$2b204`):
  - "Accolade presents": the picture, the bar's slide, then the speech, and the picture stays until the speech ends, then 5 frames (the DOS game: 3 s after the slide).
  - The showroom (overlay 1776h) keeps the first car 200 frames (DOS: 150 ticks). Its window opens one picture every 8 frames (DOS: the `.ss` file's ticks). Then the car gains 15E0h/10000h pixels a frame every frame, while its window goes on one picture every 2 frames. The second car starts with the first car's final speed, because duel never resets it (DOS: full speed). The DOS pictures and distances stay.
  - 5 frames, then the title (overlay 1390h). duel shows its "duel" picture with "The Duel", dissolves (at CPU speed), plays "Test Drive II" while it morphs the logo lines for 111 frames, and holds the title 220 frames (`$2b304`). The DOS title keeps its own morph and 1 s wait. After its reveal it now stays until both speeches end, then 220 frames (DOS: 3 s).
  - The high scores are a DOS screen and keep the DOS pace. The DSI logo and credits keep it in the DOS form; in the Amiga form they are duel's (below), with duel's frames but for the credits' hold.

## The Amiga graphics backend

The design, and what is done.

- **Five planes.** The Amiga backend (`--amiga-graphics`, `platform/gfx_amiga.c`) is the EGA backend's model and code run with a fifth plane, so the screen, every off-screen buffer and every colour have five bits: the Amiga's 32 colours. The EGA backend is a literal transcription whose register quirks shape the frames, so reusing it keeps those frames exactly; a new chunky backend would have had to rebuild every quirk. `gfx_ega.planes` is 4 or 5. The RAM paths loop over the planes, and a buffer's plane 4 is one more block after plane 3 (`ram_plane`). The screen paths take "all planes" (0Fh in the original) as all five.
- **Colours.** Each target, the screen or an off-screen buffer, has its colours: the EGA palette, or the 32 colours of the Amiga picture drawn into it (the top 4 bits of each CMAP component, as the Amiga shows them). A page drawn off-screen brings its colours to the screen when it is shown there, by `screen_reveal`'s dissolve or a blit of the buffer, as an Amiga screen brings its palette; clearing a whole target gives it the EGA palette again. The game passes EGA colour numbers (and FFh or FFFFh for white, which four planes read as 15); with five planes each draws the nearest colour of the target's palette (`ega_colour`, `gfx_amiga_colour`), and `AMIGA_PEN(n)` draws pen n itself. The scene's road and sky writers clear plane 4 where they draw.
- **Screens.** The Amiga screens are laid out their own way (the option screen is one picture with empty boxes for the car and scenery icons, at other places than DOS's), so each screen gets its Amiga form in the flow code, from what `duel` draws there, behind `gfx_amiga_screens()`. Done: the scenery choice (`scenery_select`): the scenery's picture `<prefix>icon` fills the page and the disk name is written over it in pen 5, with no line at the bottom (`duel` `$2d8c8`). The prefixes are `scen/sc1_` (Master), `scen1/scen/rock_` (California), `scen2/scen/euro_` (Europe) and `scen3/scen/euro_` (Northern Germany). The option screen (`main_menu`, `duel` `$2e07c`): the picture `pics/gameoptionscreen`, each car's logo (sprite `rcar` of `<car>logo.shp`, its hot spot at x + 22h, BEh for the box at x = 7 + 4Eh·i) and the scenery's icon (`scn0` of `<prefix>gameoption.shp`, at its own place); "N/A" in pen 1 where one is missing. Its highlight is three rectangles round the selected box, in pen 14 in the top row and 16 in the bottom row (`$2dc40`, boxes at `$24bb4` in the DOS icon order). The speedometer's and the tachometer's needles (`$1ad0a`) are lines from the hub (`<car>.b` 2EEh and 2F0h, x and y bytes) to the tip of a table (speed: 32Ah, one x, y pair a mph from the speed at 18h; revs: 4D8h, one pair each 64 rpm, at least 800 rpm). duel draws them into a one-plane buffer and blits it through the gauge's mask for the wheel's pose (`spm0`, `spm1`, `spmC`; `tcm…`; the F40 has only the `C` ones), which clears planes 1 to 4 and sets plane 0, so the needle is pen 1. The gear gate (`gbox`) is XORed on when shown (`$18c56`), and the knob (`gnob`) is a hardware sprite at its gear's place (`<car>.b` from 28h, neutral first; the +80h, +2Ch duel adds are sprite coordinates). The port draws all of this over TD2's race. TD2's view (320 × 92 at line 19) and mirror are drawn by TD2 into buffers with the road colours (the view's buffer keeps the screen's colours when shown, `gfx_amiga_keep_screen_colours`); the view's last rows are repeated down to the hood, the sky colour fills the lines above it, and the mirror's picture moves into duel's frame (line 20). The scenery's parts take duel's pens from the road data's header words ($1678e copies them; `$1789c` fills a span with the pattern of a colour index, ten bytes each, and the indices are pens): the ground left of the road 0Eh, right of it 18h, the sky 1Ah (`$1876a`), the band beyond the right ground 1Ch, and on a normal line (`$185b4`) the left shoulder 10h, the road 22h and the right shoulder 14h, each in bands with the next word (12h, 24h, 16h). duel's tunnels (`$184b2`): bit 7 of a road segment's flag byte starts or ends a tunnel, as in TD2 (record 31 in every DOS stage). On the lines between its ends duel fills the walls from the near end's edges to the road in pen 1Eh and the road in bands of 26h and 28h (20h, 2Ah and 2Ch when A4 − 3A98h is clear, which the race sets, `$1bc6a`); the Master, California and European sections give pen 20 for the walls and 24 and 23 for the road. In the Amiga form TD2's tunnel keeps its geometry and takes these pens: its black and grey (the walls, the mouth, the inside) the walls' pen, its road the tunnel road's bands, and its white ribs duel's pen 22 (`$17b88`). The port puts them into TD2's colour words (col_left, col_right, col_sky, col_far, col_shoulder) as Amiga pens and maps TD2's road grey (colour 7) to the road's pen; TD2's scene raster draws the pens on Amiga targets (`gfx_ega_scene.c`). TD2's sprites are duel's: the Amiga backend's blit (`gfx_amiga_blit`) draws, for a DOS archive registered with `gfx_amiga_substitute`, the Amiga sprite of the same name (as it is, in capitals or in small letters: TD2's lowercase `lg00` is duel's `LG00`) with its hot spot at the DOS sprite's, and leaves out the DOS masks (AND blits), as duel's sprites carry their own. Each race archive gets the Amiga archive with most of its sprites by name and size (`gfx_amiga_substitute_best` over `<scenery>*.shp`, `pics/road.shp` and the opponent's `<car>road.shp`): the Master scenery's traffic TDS2CAR1 is `sc1_mercedes.shp`, CAR2 `sc1_thunderbird.shp` and CAR3 `sc1_van.shp` (their sizes agree exactly), TDS2DEST `sc1_desertmountain.shp`, COP and ROAD `pics/road.shp`. Any other DOS sprite drawn on a target with Amiga colours (one without a twin, or the messages over the road) is drawn into a scratch buffer and then pixel by pixel in the nearest of the target's colours. The wheel follows TD2's poses (a quarter of the lock), the needles TD2's speed and revs, the gate TD2's showing and hiding, and the knob TD2's knob position carried over linearly to duel's gate (x from neutral to second gear, y from neutral to first). When any of them moves, the dashboard below the hood comes back from the picture as drawn (`gfx_amiga_keep_lines`, `gfx_amiga_restore_rect`) and all of them are drawn again. The crash draws `hdcr` in place of TD2's hood sprites. The small gauges (`$1ab60`) are turbo, oil temperature, oil pressure and fuel, each a table of 84h bytes in `<car>.b` from 0DAh (the needle's centre, then 32 tips, x and y words; no gauge where the centre's x is 0). For a gauge whose value changed, `$1ab12` draws its face (`trb0`, `oilt`, `oilp`, `fuel` of `<car>dash.shp`), the needle from the tip to the centre in pen 16, then the part of the wheel over it for the pose (`trs`, `olt`, `olp`, `fue` with 0, 2 or 1 for whl0, whl1 and straight). Each value is a 16-bit number of which the gauge shows the top 5 bits: the oil temperature (−$bc0) rises by the revs / 128 a frame (at least 800 rpm) from 0 at the start, the oil pressure is 7FFFh − temperature / 2 + revs · 6 + 5000, and the fuel is what is left of the section's. A car with a word at `<car>.b` D8h (the Corvette ZR1) has a fuel bar instead, 9 × 12 in pen 12 filled from below in pen 18. The turbo's value (−$3094, halved) is not an engine figure but the turbo sample's volume: duel's sound driver keeps four channel records of 1Eh bytes from −$30de, and −$3094 is the high word of channel 2's 16.16 volume at +0Eh. Channel 2 plays `<car>turbo`, and the race step (`$1d118`) ramps its volume one step a frame towards 0 to 64: (revs − 2000) · 831h / 65536 for revs up to 4000 with the throttle on in gear, plus (speed − 20 mph) / 4 up to 32 (with the throttle off, only the speed part; braking, 0). The port computes that aim from TD2's car as the sound backends get it (`race_turbo_volume`, shared with the Amiga sound) and ramps the needle at duel's pace, so the gauge works with the PC speaker too. duel's road bands (`$185b4`): each line's road and shoulders take the first or second of their pens by bit 3 of that line's distance along the road (bit 3 of −$c43). That distance is the line's depth in the slice table (+0Ch) plus the player's position (`$184aa`), and the position counts TD2's road units: duel indexes its road bytes by it (`$1739c`, one byte a unit, masked to the 128 records, as TD2's road at DS:3B51), so a band is eight units long. TD2's rows are one road unit each, so the port gives the lines between two rows the band of that row's unit, bit 3 of it. (The bands first alternated every two units, a guess, which at racing speed flashed at 15 frames a second.) duel's race loop (`$16518`) has no frame wait: it draws a frame (`$16432`), points the copper at the new screen (`$15872`) and starts the next, as fast as the machine allows, so the port's frame rate (15 a second, the DOS pace) stays. The Amiga form's lines (the small gauges' needles, the crash's cracks) are written into the planes (`gfx_amiga_line`), not drawn with TD2's line routine, which leaves the EGA bit mask at 0: TD2's own code resets it before the next blit, but the Amiga form draws its lines where that code does not run, so the next frame's copy of the view onto the screen changed nothing and the road stood still for two or three frames at a time (`tests/test_amiga_graphics.py` `test_race_view_moves`). duel's marks along the road (`$17b10`): it paints no lines (TD2's yellow centre dots and white edge dots), but at every 16th road unit it puts a post, on the left at units 0 mod 32 and on the right at 16 mod 32. A post is `pst1` to `pst4` of `pics/road.shp` (a white delineator with a black top), a quarter of the road's width out from its edge, its hot spot an eighth of the width above the row, `pst4` for rows at least 92 wide, `pst3` from 52, `pst2` from 36, else `pst1` (duel's row widths at A4 − 6842h and post sizes at A4 − 6580h); a side that drops off gets none, and a tunnel none. In a tunnel duel draws ribs every 16 units (pen 22, the frame from the road's edges up half its width) and between them, at units 8 mod 16, a lamp `lit0` to `lit4` of the section's sprite file in the middle under the ceiling (`lit4` from 133 wide, `lit3` from 71, `lit2` from 46, `lit1` from 34, A4 − 654Eh). The Amiga form draws the posts and lamps on TD2's rows (`amiga_cockpit_road_mark`, the row's road unit as for the bands) in place of TD2's dots, and keeps TD2's ribs in duel's pen. TD2 also has an open form of the tunnel (grey walls without a roof, DS:37F7). The stage file sets it, as the byte at file offset 38Dh lands there when the stage loads (road object 23 would toggle it, but no shipped stage has one): Europe's first and fourth stages and California's sixth use it, and every tunnel reached in headless runs was one of these. It gets the walls' and road's pens and no lamps. Each x has duel's heading taken off and is brought into −400..400 by steps of 800 (`$18f0a`). When the word 02h is set, the clouds drift right by 0FA0h, 1388h, 1770h and 1B58h / 65536 pixels a frame from 0 at the start. A sprite the file lacks (the desert has no `cldA`, Europe no clouds) is not drawn. ## 3. How the Amiga version fits the port

The port stays one game: the DOS game logic running the TD2EGA image. The Amiga version adds three things to it, each found and checked against the Amiga files and code:

1. **Amiga audio**, a second `AudioBackend` beside the PC speaker. The game's sound calls (effects, engine, music) become Amiga samples played on four Paula-like channels; the music player in `song` is translated to C from its 68000 code. The switch works like the graphics switch, on its own key and menu entry. Done; see "The Amiga audio backend" above.
2. **Amiga graphics**, a fourth `GfxBackend`: a 320 × 200, 32-colour frame. Screens come from the ILBM pictures, sprites from the `.shp` archives by the DOS names. Where the Amiga screens differ (the dashboard's extra instruments), the backend draws the Amiga version from the DOS game's state where that state exists.
3. **Courses.** A converter from Amiga road data to DOS stage files, checked by converting the three Amiga sets that have DOS twins and comparing with the DOS files. Then Northern Germany is converted the same way and played with the DOS game logic, in every graphics mode.

Everything is read from the user's files at run time and derived files go to the profile folder; nothing from the game is committed.

## 4. Order of work

1. **Formats.** Done: load files (with their relocations, `amiga/hunk.c`), Rpck, ILBM, the sprite archives and sprites, the race screen's palette, the raw sample header, the engine samples.
2. **Courses.** Done for Northern Germany: it is built from DOS twin stages, with its own signs (above). A general converter from Amiga road data to DOS stages is not needed for it; it would be for an Amiga scenery without DOS twins, and would need the header words and the Amiga object codes mapped.
3. **Amiga audio.** Done: the `song` player, the race driver and the race logic in C, each checked against the original; the Paula model; the game events and car state; the Amiga `AudioBackend`; the live switch (Ctrl+Shift+S and the menu). The user tested it and approved it on 25 October 2026.
4. **Amiga graphics.** Done: the five-plane backend, the sprite decoder, every screen of the game in duel's form (section 3) and the live switch.
5. **Data manager.** Done: the `amiga` setting names the Amiga game's folder or archive, `app_data_amiga_dir` finds the folder with `duel` and `sfx`, and the sound, the graphics (`gfx_amiga_open`) and Northern Germany (`add_northern_germany`) all take it from there.

## 5. Open questions

- Answered: the Amiga's extra instruments change nothing a player would notice. The oil temperature (A4 − BC0h) and oil pressure (A4 − BBEh) are read only by their gauges (`$1ac62`, `$1ac7c`) and their own update (`$1adfa`, `$1ae34`); the temperature rises with the revs and stops at FFFFh. The fuel (A4 − 2A46h) runs the out-of-gas logic (`$15c42`, `$16498`), as TD2's fuel does.
- Answered: Northern Germany has seven stages in duel. duel takes the stage count from the first word of the scenery's `roaddata0` (`$16642` into A4 − 2A44h, read for the first stage) and races until the stage number reaches it (`$160e8`); `scen3`'s `euro_roaddata0` says 7 (Master 6, California 7, Europe 6), though its title picture names six places. The port's seven-stage build matches.
