# Amiga version: files, findings and plan

Started 24 October 2026. The source is the user's archive `reference/amiga/TestDrive2&DataDisks_v1.1_HD_JOTD.lha`: Jean-François Fabre's HD install of the Amiga game with its car and scenery disks. `docs/planning/amiga-evidence-and-plan.md` is the earlier inventory (file hashes and first bytes); this file replaces its plan.

For the tools, unpack the archive once into `runs/amiga` (gitignored): the app does this itself when the archive is added under Game files, and `runs/amiga` is a copy of that folder. All tools below read from there.

## 1. What is in the archive

| Folder | Content |
|---|---|
| root | `duel` (the game), `DuelHD` (the HD patch loader), the catalogues `cars.dat0`, `scen.dat0`, `select.dat0` |
| `cars` | Ferrari F40 and Porsche 959 (base disk) |
| `cars1` | The Muscle Cars: `camo`, `dodge`, `gt500`, `gto`, `stingray` |
| `cars2` | The Supercars: `coun`, `lotu`, `ross`, `ruf`, `vett` |
| `pics` | title, option and difficulty screens, game over, end game, the road sprites |
| `scen` | Master Scenery (`sc1_`, 6 stages) |
| `scen1` | California Challenge (`rock_`, 7 stages) |
| `scen2` | European Challenge (`euro_`, 6 stages) |
| `scen3` | Northern Germany Challenge (`euro_` names again, 7 road files). Its title picture reads "2012 Janusz_Mombasajoe" and names Ostsee, Lüneburger Heide, Wesertal, Teutoburger Wald, Harz and A7. |
| `sfx` | samples and the music player `song` |

The catalogue files have the same records as the DOS `CARS.DAT` and `SCENES.DAT`: a count, then a path (`cars/p959`, `scen/sc1_`) and a display name per entry, big-endian.

**Northern Germany is built from the other sets.** Every sprite file in `scen3` is a byte copy of a Master, California or European file, under another name (for example its `euro_mercedes.shp` is the European `euro_thunderbird.shp`). Six of its seven road files are copies of stages of the other sets, for example `euro_roaddata4` is the Master `sc1_roaddata4`. New are `euro_roaddata1`, six of the seven sign files, the title picture `euro_icon` and its high scores. So Northern Germany can also be shown with the DOS art of the sets it borrows from, once each Amiga set is matched to its DOS set.

## 2. File formats found

- **Program files** (`tools/amiga/hunk.py`). `duel` is an AmigaDOS load file: 71 KB code, 31 KB data, and an overlay node of 21 KB code. It is compiled C (Lattice/SAS style: small data through A4, `link`/`unlk` frames), with no symbols. `sfx/song` is a separate load file with its symbols: the music and effect player (`_PlaySong`, `_PlaySfx`, `_StopSong`, `_FadeSong`, `SongInt` and so on, 3 KB of code) and 21 KB of chip-memory data (the song and its instruments). `tools/amiga/disasm.py` disassembles with Capstone's 68000 mode at the addresses `hunk.load` gives.
- **Rpck packing** (`tools/amiga/rpck.py`). 177 files start with `Rpck`, the unpacked size and a run-length stream: a signed count byte, a run of `n + 1` copies for `n ≥ 0`, `-n` literal bytes otherwise. The loader is at `$1e5d0` in `duel`, the unpacker at `$1e518`. `tests/test_amiga_files.py` runs the game's own unpacker under Unicorn (as a 68000) on all 177 files and compares with the Python one: all match. Six streams write one byte past the stated size; the game's buffer takes it.
- **Pictures** (`tools/amiga/ilbm.py`). Full screens (title, options, difficulty, the dashboards, the rear views, the scenery title pictures, the gas stations) are IFF ILBM, 320 × 200, 5 bitplanes (32 colours), ByteRun1. The `.p` files are ILBM palettes alone. The `.sb` files are 640 × 200 in 4 colours. All decode and look right.
- **Sprite archives** (`.shp`, Rpck-packed; `tools/amiga/shp.py`). They are the DOS archive layout, big-endian: a long (`PPkc` or a size), an entry count, the 4-character names, the offsets, the data. The names follow the DOS names, so a DOS sprite can be matched to its Amiga sprite by archive and name.
  - Each sprite is a 20-byte header and its bitplanes, one after the other: width in bytes, height, hot spot x and y, screen position x and y, two bytes of planes set to one wherever the sprite is drawn, and up to six bytes that say which screen planes each stored plane goes to (a stored plane may go to several, `03` or `1f`). Colour 0 where no stored plane is set is transparent.
  - Checked: the dashboard's turbo gauge and fuel and oil gauges, drawn at their stated positions, equal the dashboard picture pixel for pixel (a test in `tests/test_amiga_files.py`). The roof, pillar, mirror, hood and steering wheel land where they belong.
  - Open: the race screen's palette. The cockpit sprites drawn with the dashboard picture's palette give some wrong colours (the steering wheel, the gear gate), so the race screen probably changes colours part way down. To be read from `duel`'s screen setup.
  - Not all names match. The DOS archives keep separate EGA masks (`fc0M` next to `fcr0`). The Amiga road archive also holds the police car, which DOS keeps apart. The Amiga dashboard has more instruments (`fuel`, `oilp`, `oilt`, `trb0`, `swhl`).
- **Road data.** The DOS stage `.DAT` holds what the Amiga version splits over `roaddata<n>`, `slicedata` and `vectorsigns<n>`. `tools/dos_unpack.py` unpacks DOS files in Python (Huffman and RLE passes, archive entries) for these comparisons.
  - **DOS.** The road is a byte per road unit from DGROUP 3B51h (stage file offset 6E7h). Bit 7 is a side flag, and the low 7 bits index the stage's 128 records of 4 bytes at 347Eh (file offset 14h): flags, curve, pitch, object. The curves in those records run 0, 1, 2, 4, 6, …, -1, -2, -4, ….
  - **Amiga.** `roaddata<n>` is a header of 125 words, then the road bytes up to an `FF`. The loader is `$165ec`: it copies header words into game variables (many times 10) and takes the road length as the byte count less 2Dh. The header also names scenery sprite files (`desertmountain.shp`). `slicedata` is the same file in every scenery, and its values are the DOS record curves times 8, so it is the Amiga record table.
  - **Pairing.** The Master stages pair by number: each Amiga road is a little longer than its DOS twin (1426 against 1342 units for stage 0, and so on for all six). The road bytes are mostly the same runs with other record numbers (DOS `3b` where the Amiga has `46`) and some local differences.
  - **Records.** The Amiga record is two words: flags and curve (times 8) in the first, pitch and an object code in the second. Records 0–31 (straight, curves, hills, the flag records) are the same numbers in both versions. DOS records 32 and up carry the stage's own object numbers 1, 2, 3, …; the Amiga records carry global object codes, and Amiga record n is mostly DOS record n − 1 for n from 33 to 54. The Amiga uses about 40 further records (codes 16–20, 24–27, 39–41, 80–84, 88–91, 144–148, 152–155, 208–212, 216–219) that DOS does not have.
  - **Alignment.** With those rules the Master roads agree with DOS at 77 to 91 % (`difflib` over the road bytes). The rest is mostly the side flag: the Amiga sets bit 7 over long stretches where DOS has it clear, and the run lengths differ a little.
  - **Open question (timeboxed, 24 October 2026).** How the Amiga game reads the road bytes: where the side flag and the extra records come from, and why its roads are 3 to 6 % longer. The answer is in the code that walks the road bytes in `duel` (the consumer of `$26222`, the road start the loader sets). Until then there is no exact converter, and Northern Germany's new road (`euro_roaddata1`) cannot be converted. Its six copied roads can use the DOS twins of their source stages.
  - Still to map: the header words and the DOS stage fields (the ratings are there: Amiga 70, 110, 150 mph against DOS 80, 110, 150).
  - **Northern Germany's roads** are, in order: California 6, a new road, Europe 3, California 2, Master 4, Europe 5, Europe 1.
- **Decompiling.** `tools/amiga/ghidra.ps1` lays out `duel` with `hunk.py`, imports it into Ghidra as 68000 code with A4 = `$2957e` (Lattice small data), marks a function at every `link a5`, and writes all 451 functions to `runs/amiga-ghidra/duel.c`. Global variables come out as their absolute addresses.
- **Sound.**
  - Five IFF 8SVX samples: `accolade`, `test_drive_ii`, `the_duel` (speech), `starter`, `gameover`.
  - Six raw samples with a small header: `Bump`, `crash`, `shortcrash`, `radar`, `siren`, `Squeal`. The race loads them in `$1cd1a` (short crash or crash by a setting); `$1ce50` plays the siren with its pitch swept between 14,000 and 23,000.
  - Each car's `engine` and `turbo` files (Rpck-packed in some cars).
  - `song`: the player and its data (below).

### The race sounds (in `duel`)

The race does not use the song player. `duel` has its own sample driver and the logic that feeds it from the car's state:

- **Driver.** Four channel records of 1Eh bytes at `$264a0` (A4 − 30DEh). `$11f96` sets it up: it takes the level 4 audio interrupt (`$1226e`) and adds a vertical blank server (`$1231c`). `$120cc` plays a sample on a channel (address, length, channel, period, volume, repeats; FFFFh loops), `$12072` plays a raw sample file at period 3,579,545 / its rate, `$1218a` stops a channel, `$121ea` tells whether a channel plays, `$12202` sets a channel's period and volume, `$12250` sets a channel's volume ramp (target and step, read by the server).
- **Raw samples.** `Bump`, `crash`, `shortcrash`, `radar`, `siren` and `Squeal` are a length (long), a rate in Hz (word) and signed 8-bit data. Their rates: bump 9,400, crash and short crash 5,326, radar 20,000, siren 7,202, squeal 10,000.
- **Logic.** `$1cd1a` loads the five race effects (crash or short crash by a setting). `$1d044` starts the looping sounds at the start of a race: the squeal and the car's engine and turbo samples. `$1d118` runs each frame: the engine's period is 2,398,600 / rpm (rpm at least 800, the period kept between 82h and 708h), and its volume comes from the gear and the speed. `$1d210` and `$1d2cc` play the gear change and the bump. `$1cde4` plays the radar beep, `$1ce10` the crash, `$1ce50` starts the siren and `$1cedc` sweeps its pitch between 14,000 and 23,000 (up by 1/50 or 1/100 a frame, down by 1/100).
- **The driver in C** (`src/amiga/race_sound.c`). Checked by `tests/test_amiga_race_sound.py`: duel's own routines run under Unicorn (A4 set, the OS call and the siren call replaced by `rts`). The C driver runs from `td2diff.dll`. Both play a script of raw samples, looping and repeating samples, period and volume changes, ramps, stops and the channel 6 alias, with the server every frame and the audio interrupts from the Paula timing model. Every custom chip write matches. A sample starts at the second frame after its channel last stopped, as on the Amiga. The original's marks for the game about channel 2 change no register and are left out.
- **The logic in detail.** Channel 0 has the one-shot effects and the siren, channel 1 the squeal, channel 2 the car's turbo sample (`<car>turbo`) and channel 3 its engine sample (`<car>engine`); each car has its own pair, raw like the effects. The logic reads these duel variables: the rpm (`$261fa`), the speed in mph as 16.16 (`$2619c`), the throttle (`$260f8`: below 0 braking), whether a working gear is engaged (`$262de` indexed by the gear `$26292`), whether the engine runs (`$26b38`), the skid squeal's volume (`$289d2`, set by the cornering code `$1b292` to 25 plus a sixteenth of how far the steering is past the grip limit, at most 64), the car's and the police car's road positions (`$25228`, `$26178`) and the police car's speed (`$26180`), two bump flags (`$262d8`, `$277ba`) and the gear change squeal's step (`$234ee`, set by `$1a71e`: a start from neutral into first above 4,000 rpm squeals for 25 − (rpm − 2,200) / 256 steps, a change into second with a drop of more than 1,600 rpm for 14).
  - The engine runs at full volume with the period above. The turbo runs at the engine's period; its volume is 0 when braking, and otherwise (rpm − 2,000) / 31.25 between 2,000 and 4,000 rpm in gear with the throttle on (nothing below 2,000 rpm or out of gear), plus (mph − 20) / 4 (at most 32), at most 64 in all, reached by a ramp of one step a frame. A car record word (offset 0Ah) of 0 would add 1,500 rpm and drop the turbo an octave; every shipped car has 1 there.
  - The siren's period is its pitch × 450 / (450 − the closing speed in mph) / its length (a 24-byte wave), changing by at most 2 % a frame; its volume is 64 less half the gap to the police car in road units (at most 60 less). The radar beep, the bump and the siren all use channel 0: the radar is not played during the siren or after a crash, the bump only when channel 0 is free.
  - duel calls Delay and WaitTOF between some plays; the C leaves them out, because the driver starts a sample no earlier than the second frame after its channel stopped anyway.
- **The logic in C** (`src/amiga/race_logic.c`). Checked by `tests/test_amiga_race_logic.py`: duel's routines from `$1cd1a` to `$1d30a` and its driver run under Unicorn, the C logic and driver from `td2diff.dll`. Both get the same car state (written into duel's variables for the original) over 450 frames of a scripted drive: revs through the gears, braking, coasting, a police car closing and falling back, radar beeps, bumps, gear change squeals, the siren started and stopped, a crash, a fade-out and a second start. Every custom chip write matches, and the test makes sure the siren swept, the gear change squeal played, the engine followed the rpm and channel 0 started its effects.

### The music and effect player (`sfx/song`)

- **What it is.** Accolade's player, 3 KB of 68000 code with its symbols, and 21 KB of chip data: one song (`titlesong`, four tracks), four instruments (bass, bass drum, snare, breathy flute, each an 8SVX in the file), the period and note length tables. Its entry point takes a command in D0: 0 open, 1 read the instruments, 2 play the title song, 3 stop, 4 close, 5 status, 6 fade, 7 play an effect (an 8SVX, channel, volume, repeats, music volume while it plays), 8 stop an effect, 9 effect status, 10 pause, 11 resume, 12 change an effect's rate and volume.
- **How it runs.** `SongInt` is a CIA-B timer A server; the song sets the timer itself (commands DD and DE, `3c00h` for the title song, about 46.6 ticks a second). Each tick reads note and command bytes per track, sets the voice, and starts notes with the period table, octave selection and vibrato or arpeggio. `SongIntHandler`, the audio interrupt, queues each sample's loop part or stops a one-shot. Effects take a channel from the music until they end.
- **In C** (`src/amiga/song.c`, from the disassembly, routine by routine). The song file is laid out by `amiga_mem.c` at the addresses `hunk.py` uses, and the player finds its variables by the file's symbols. Custom chip and CIA writes go through a hook.
- **Checked** (`tests/test_amiga_song.py`). The original runs under Unicorn and the C player runs from `td2diff.dll`. Both get the same timer ticks and audio interrupts, and a Paula timing model takes the interrupt times from the original's own register writes. Every custom chip and CIA write is the same, in order: 6,000 ticks of the title song (128.7 s, 1,986 notes, 1,546 interrupts), and a script with effects, rate changes, pause, resume and fade. The original has one oddity the C keeps: when it stops it clears the interrupt requests by writing to INTREQR, a read-only register, so that write does nothing.
- **Paula** (`src/amiga/paula.c`). Four DMA channels and the timer from the same register writes, mono output with each byte held for its period, and a one-pole 4.4 kHz low-pass like the Amiga 500's fixed filter. It uses the NTSC clocks (3,579,545 Hz, CIA 715,909 Hz), because the player's effect periods are computed for NTSC. `python tools/amiga/play_song.py runs/amiga/sfx/song out.wav 130` renders the title song with it. Nobody has listened to it yet.

### The Amiga audio backend

`src/amiga/audio_amiga.c` is a second `AudioBackend` beside the PC speaker. The DOS game logic runs as before, speaker writes included; the Amiga backend ignores those and plays from the game's sound events and car state instead (`audio_backend.h`):

- **Events.** `music_play` reports its song, `run_stage` the start of each life (with the player's car code) and its end, with a crash or a blown engine before it, and `hit_object` the bump. Song 1 (title and menus) becomes the Amiga title song, reloaded from the file each time because the player edits its data. Songs 2 and 3 (the police ending) are silent: the Amiga game has no other song. A life's start stops the music, loads the car's engine and turbo samples (the DOS car codes map to the Amiga file names, `F40` to `cars/f40`, `GOAT` to `cars1/cars/gto` and so on) and starts the loops; its end fades them out and stops the siren.
- **Car state.** Ten times a second, at the start of the simulation's 10 Hz step, `sim.c` reports the rev counter's rpm, the speed, throttle, gear and whether it works, the skid (how far the steering is past the grip limit), the siren and radar flags, and both cars' positions and the police car's speed. The backend turns that into duel's variables, starts the gear change squeal as `$1a71e` would from two consecutive states, starts and stops the siren and the radar beep on their flags' changes, and runs duel's physics step `$1d118`. The vertical blank server (the siren sweep, then the driver) runs at the NTSC frame rate inside the Paula model.
- **Guesses.** duel runs its physics step about as often as the DOS game does (its free-revving adds 700 rpm a step where DOS adds 600 at 10 Hz), so the logic runs at 10 Hz. Road units and the steering scale are taken to be the same in both versions. Neither has been compared with a running Amiga.
- **Files.** The Amiga game's folder or archive is the `amiga` setting, chosen in the menu (Sound, "Amiga game files…") or when Amiga sound is first picked; `app_data_amiga_dir` finds the folder with `duel` and `sfx` in it, unpacking an archive into the profile first. The backend reads `sfx/song` and the five race effects at start and the car samples at each life's start.
- **8SVX sounds.** duel plays its one-shot 8SVX sounds through an overlay stub (`$21a10`; the overlay node's code at 5178h). That routine calls the music player's effect command 7 on channel 2, at volume 64, once, with the music at 69h meanwhile. The game over screen (`$13bc6`) plays `sfx/gameover` with it, and the title sequence (overlay code 13C6h–1640h, with `pics/title.shp`) plays `sfx/the_duel` and then `sfx/test_drive_ii`. The backend does the same at the DOS game over screen and at the DOS title picture ("tdri" and "duel"); the second speech sample starts when the first ends, where duel draws in between (a guess). `the_duel` and `test_drive_ii` are Rpck-packed; the backend unpacks them like duel's loader.
- **Not played yet.** `accolade` and `starter`. No code in `duel` names them (perhaps the launcher `DuelHD` does).
- **Checked** by `tests/test_amiga_audio.py` through the backend's own interface: nothing sounds before an event; the title song, the speech over it, the race (the engine's pitch follows the rpm), the siren, the crash and the game over sound all sound; the race end fades the car out; the police ending's songs are silent. The C Rpck unpacker gives the same bytes as `tools/amiga/rpck.py` for the three 8SVX files.

## 3. How the Amiga version fits the port

The port stays one game: the DOS game logic running the TD2EGA image. The Amiga version adds three things to it, each found and checked against the Amiga files and code:

1. **Amiga audio**, a second `AudioBackend` beside the PC speaker. The game's sound calls (effects, engine, music) become Amiga samples played on four Paula-like channels; the music player in `song` is translated to C from its 68000 code. The switch works like the graphics switch, on its own key and menu entry. Done; see "The Amiga audio backend" above.
2. **Amiga graphics**, a fourth `GfxBackend`: a 320 × 200, 32-colour frame. Screens come from the ILBM pictures, sprites from the `.shp` archives by the DOS names. Where the Amiga screens differ (the dashboard's extra instruments), the backend draws the Amiga version from the DOS game's state where that state exists.
3. **Courses.** A converter from Amiga road data to DOS stage files, checked by converting the three Amiga sets that have DOS twins and comparing with the DOS files. Then Northern Germany is converted the same way and played with the DOS game logic, in every graphics mode.

Everything is read from the user's files at run time and derived files go to the profile folder; nothing from the game is committed.

## 4. Order of work

1. **Formats.** Done: load files, Rpck, ILBM, the sprite archives and sprites. Next: the race screen's palette, the raw sample header, the engine samples.
2. **Courses.** Map `roaddata`, `slicedata` and `vectorsigns` to the DOS `.DAT` and `.SGN`, using the Master scenery's six stages against `TDS20`–`TDS25`. Then California and Europe against `CCC` and `EC_`, then Northern Germany. Match each Amiga sprite set to its DOS set.
3. **Amiga audio.** Done: the `song` player, the race driver and the race logic in C, each checked against the original; the Paula model; the game events and car state; the Amiga `AudioBackend`; the live switch (Ctrl+Shift+S and the menu). Next: a listening test by the user.
4. **Amiga graphics.** The sprite decoder, the backend, the screens, the switch.
5. **Data manager.** Done for the sound: the `amiga` setting names the Amiga game's folder or archive, and `app_data_amiga_dir` finds the folder with `duel` and `sfx`. Next: the same source for the Amiga graphics and Northern Germany.
